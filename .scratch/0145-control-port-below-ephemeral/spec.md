# 后台控制端口移到临时端口段以下

## Problem Statement

后台管理进程的控制端口由当前用户名和家目录的散列值确定, 现在落在 30000-49999. 这一段与两类操作系统的动态端口范围重叠, 管理进程启动时绑定该端口可能失败:

- Linux 默认临时端口段是 32768-60999, 内核为回环出站连接自动分配本地端口时可能占用同一端口, 此后绑定得到 `EADDRINUSE`. 控制端口落在该段内的用户约占 86%.
- Windows 默认动态端口段是 49152-65535, Hyper-V, WinNAT, WSL 等组件在其中保留端口块, 保留范围随重启变化, 落入其中的监听得到 `EACCES`, 重启之前管理进程都起不来, 依赖后台 Agent 的 Reviewer 门禁也跑不了. 控制端口落在该段内的用户约占 4%, 保留块可能落在 30000-49999 内.

早先的长期规范把这一风险写成 "接受的代价" 并保留了端口. 维护者在 2026-11-18 改为整段移走. 维护端口已在 effort 0102 移到 20000-29999, 同一机制造成过真实故障.

## Solution

控制端口改为 `30000 + h % 2768`, 范围 30000-32767, 位于 Linux 临时端口段 (32768 起) 和 Windows 动态端口段 (49152 起) 之下. `h` 仍是当前用户名和家目录 (以 NUL 分隔) 的 SHA-256 前 4 字节按大端读出的无符号整数, 散列输入不变.

升级时新版本的安装器先经此前版本的控制端口停止旧管理进程, 再写入载荷, 之后所有客户端和新管理进程只使用新端口.

## User Stories

1. 作为 Linux 用户, 我希望控制端口不与回环出站连接的临时端口相撞, 以便后台管理进程不会因此启动失败.
2. 作为 Windows 用户, 我希望控制端口不落入系统保留的动态端口块, 以便重启后后台管理进程和依赖它的 Reviewer 仍能使用.
3. 作为升级 ARW 的用户, 我希望安装器先停止此前版本的管理进程再写入载荷, 以便升级不留下旧代码管理进程.
4. 作为端口被其他服务占用的用户, 我希望得到明确的失败而不是误判或静默写入, 以便释放端口后重试.

## Implementation Decisions

### Port formula and ranges

| 端口 | 公式 | 范围 | 状态 |
| --- | --- | --- | --- |
| 控制端口 | `30000 + h % 2768` | 30000-32767 | 本次新定 |
| 此前版本的控制端口 | `30000 + h % 20000` | 30000-49999 | 只供升级时停止旧管理进程 |
| 维护端口 | `20000 + h % 10000` | 20000-29999 | 不变 |

公式不随平台变化, Windows 与 Linux 取同一个值. 新范围不与两类操作系统的默认动态端口段相交, 所以 Linux 上的临时端口相撞和 Windows 上的保留块不再影响控制端口. 管理员把动态段调低或在 30000-32767 内手工设置排除范围的机器不在保证之内, 不为它们增加回退, 与维护端口的取舍相同.

### Occupied port

新范围只有 2768 个槽, 而且与 Kubernetes NodePort 默认段 30000-32767 重合, 本机运行的容器编排或其他服务也可能监听同一端口. 控制端口固定且不可配置, 被其他进程占用时不探测其他端口, 不回退:

- 管理进程启动时绑定控制端口失败 (Linux 为 `EADDRINUSE`, Windows 上被保留或占用为 `EACCES` 或 `EADDRINUSE`), 进程退出, 客户端按既有规则立即报告 `Background Agent manager exited during startup (<退出码或信号>)` 及子进程的标准错误, 明确失败, 不会被误判为维护进行中. 用户释放该端口后重试即可.
- 安装, 更新和卸载的维护请求连到被其他进程占用的控制端口时, 鉴权失败, 维护返回 `unknown` 并给出原因, 不继续写入; 释放该端口后重试.

被拒绝的方案: 端口被占用时改用散列的下一个槽. 客户端和安装器必须发现管理进程实际使用的端口, 这需要持久记录或逐个探测并向未知服务发送鉴权握手, 新增状态和协议, 而 2768 个槽中某个用户的那一个恰好被占用的概率与其本机在该段内的监听数成正比, 通常很小, 失败明确且可由用户恢复, 不值得为它引入这些机制.

### Upgrade

安装, 更新和卸载经 `acquireBackgroundAgentMaintenance` 取得维护互斥后, 向正在运行的管理进程发送 `__maintenance` 请求. 使用默认端口时, 请求顺序是:

1. 向控制端口发送. 取得响应时按原规则处理 (`ready` 后核对管理进程退出, `busy` 与 `unknown` 原样返回); 失败且不是 `ECONNREFUSED` 时按原规则返回 `unknown`.
2. 控制端口得到 `ECONNREFUSED` 时, 若此前版本的控制端口与控制端口不同, 再向此前版本的控制端口发送同一请求, 取得响应后按同一规则处理. 向此前版本的控制端口的发送在任何失败时都视为那里没有此前版本的管理进程, 不报告错误: 此前版本的控制端口落在 30000-49999 内, 可能被无关服务占用, 也可能落入 Windows 保留块 (连接得到 `ECONNREFUSED`), 管理进程若真在那里就必然监听着它. 此后既有的管理进程缺席核对 (进程身份观察) 仍保证旧管理进程确实不存在, 否则维护返回 `unknown`.

升级后新管理进程只监听控制端口, 客户端不再向此前版本的控制端口发送任何请求.

跨版本组合:

| 组合 | 结果 |
| --- | --- |
| 新安装器, 旧管理进程在运行 | 先经此前版本的控制端口停止旧管理进程, 再写入载荷, 之后首个客户端启动新管理进程 |
| 新安装器, 新管理进程在运行 | 经控制端口停止, 不触碰此前版本的控制端口 |
| 新客户端 (源码检出), 已安装的旧管理进程在运行 | 控制端口没有监听, 客户端启动已安装的旧代码管理进程, 它绑定此前版本的控制端口得到 `EADDRINUSE` 而退出, 客户端明确报告启动失败; 先运行 `node install.mjs` 即可恢复 |
| 新客户端 (源码检出), 没有管理进程在运行, 已安装的仍是旧版本 | 客户端启动已安装的旧代码管理进程, 它成功绑定此前版本的控制端口, 新客户端只连新控制端口, 等到消息预算用尽后报告超时, 旧代码管理进程留在此前版本的控制端口上; 运行 `node install.mjs` 即可恢复: 安装器经此前版本的控制端口停止它. 这两行只有维护者运行源码检出时会遇到, 与既有的 "源码入口与已安装版本不一致" 同类, 修改管理进程一侧代码后须重新安装 |
| 旧客户端, 新管理进程 | 旧客户端连此前版本的控制端口, 得到连接被拒或鉴权失败, 视为管理进程不可用; 旧版本的安装器已被新版本的安装覆盖, 实际只在降级后出现 |

过渡机制的取舍: 其他可行方式是新管理进程在过渡期同时监听此前版本的控制端口, 或不经端口而按进程身份直接结束旧管理进程. 前者让新管理进程继续绑定可能落入动态段的端口, 重现本 effort 要消除的故障, 并要求两个监听长期并存; 后者绕过 `__maintenance` 的忙闲判断 (忙时拒绝停止) 和优雅退出, 且各平台的结束方式不同. 经此前版本的控制端口发送 `__maintenance` 复用既有的停止协议和缺席核对, 只增加一次向旧端口的请求; 代价是升级时多一次连接尝试, 且安装器必须保留此前版本的控制端口的计算直到停用.

此前版本的控制端口的兼容步骤是过渡机制, 以后可以像 effort 0104 停用兼容维护端口那样, 由维护者另行决定停用, 本 effort 不决定时机.

## Testing Decisions

- 端口值: 对默认控制端口断言落在 30000-32767, 对此前版本的控制端口断言落在 30000-49999, 防止控制端口回到动态端口段.
- 升级与占用: 沿用客户端测试里已有的假控制服务器 (进程内回环服务, 不起真实管理进程), 控制端口用关闭端口, 此前版本的控制端口经 `legacyPort` 传入. 按风险分组观察: 此前版本的管理进程应答 `ready` 时被停止并返回 `acquired`, 应答 `busy` 或 `unknown` 时原样返回且不继续; 两个端口都无人时按原有的离线路径返回 `acquired`, 不阻断升级; 此前版本的控制端口被不响应鉴权的其他服务占用而缺席核对不是 `absent` 时返回 `unknown`, 证明吞掉发送失败后仍由缺席核对兜底; 控制端口被其他服务占用时返回 `unknown` 且不向此前版本的控制端口发送. 管理进程启动时绑定失败的明确失败由既有的启动失败测试覆盖, 不另加.
- Windows 与 Linux: 公式和请求顺序与平台无关, 测试不含平台分支, 两个平台运行同一组测试 (验收: 新增测试没有 `process.platform` 判断). Windows 保留块上的 `EACCES` 发生在服务端监听, 客户端侧只看到 `ECONNREFUSED`, 与关闭端口相同, 所以上述关闭端口的案例就覆盖这一情形; 不为它制造保留块 (需要管理员权限).
- 不做真实跨版本安装或真实管理进程测试: 行为完全由两个端口上的连接结果决定, 假服务器已制造每种持有关系; 冒烟验证在实施后本机重新安装时手工进行一次.

## Out of Scope

- 不加控制端口回退或可配置端口.
- 不决定此前版本的控制端口兼容步骤的停用时机.
- 不改变维护端口, 鉴权, 协议和管理进程其他行为.

## Module Design

### Modules

后台 Agent 客户端 Module 继续拥有端口计算和维护互斥的取得, 新增的责任只是在维护互斥中向此前版本的控制端口发送一次回退请求. 其他 Module (后台管理进程, 安装, 卸载) 的责任不变, 仍只调用客户端 Module.

### Interfaces

- 控制端口计算 `backgroundAgentPort()` 返回新公式的值; 新增导出的 `backgroundAgentLegacyPort()`, 返回 `30000 + h % 20000`, 只供维护互斥使用.
- `acquireBackgroundAgentMaintenance` 增加参数 `legacyPort`, 默认值按 `port` 的值决定: `port` 等于默认控制端口时为 `backgroundAgentLegacyPort()`, 否则为 `null` (不回退); 显式传入默认控制端口与省略等价, 结果类型, 错误和 `busy`, `unknown` 的含义不变. 调用方 (安装, 卸载) 不传该参数.
- 管理进程, 客户端和守护进程的 `port` 参数含义不变.

### Seams and Adapters

不新增 Seam. 测试经已有的 `port` 参数与新增的 `legacyPort` 参数传入临时端口, 不起真实管理进程.

### Dependencies and Data Flow

依赖方向不变. 两个端口值只在客户端 Module 内由用户名和家目录计算, 经参数向下传递, 不写配置或持久状态.

### Module Design Rationale

此前版本的控制端口的回退放在维护互斥一处, 因为只有安装, 更新和卸载需要停止此前版本的管理进程; 普通客户端不回退, 避免新旧管理进程长期并存的歧义. `legacyPort` 默认值随 `port` 而定, 使指定了临时控制端口的测试不会连到真实机器上的旧管理进程, 同时生产调用方无须传参. 向此前版本的控制端口的发送吞掉全部失败, 依据是管理进程缺席核对: 超时或鉴权失败并不能证明旧管理进程不存在, 真正使这一选择安全的是随后的进程身份核对, 它不是 `absent` 时维护返回 `unknown` 而不写入. 接受的代价: 活着的旧管理进程恰好不应答时升级以 `unknown` 失败, 重试即可; 不能省略缺席核对.

### ADR Evaluation

权威来源不变: 端口仍由用户名和家目录确定, 不读配置. 不增加持久状态, 恢复合同不变: 旧管理进程由安装器停止, 停止后由进程身份核对确认. ADR 0030 (后台 Agent 用户级管理) 所述固定本机回环端口的取舍不变, 不需要新 ADR.
