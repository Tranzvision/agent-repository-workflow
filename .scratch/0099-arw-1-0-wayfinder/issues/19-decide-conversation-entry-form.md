# 确定 Engine 对话入口的形态

Type: grilling
Status: resolved
Blocked by: issue:0099:07

##### Question

Engine 对入口提供与形态无关的会话事件流和命令接口 (见 [定义 Engine 驱动流程的运行合同](07-define-engine-runtime-contract.md)), 首版用户实际通过什么与 Engine 对话: Engine 自绘的终端界面, Engine 在本机回环地址上提供的网页, 还是复用 Codex 与 Claude Code 自己的交互界面并经 hook 等扩展点接入? 是否另外把 Engine 暴露为 ACP agent, 让支持 ACP 的编辑器和客户端作为前端? 远程与手机使用, Windows 原生 PowerShell 是否为首版硬要求? 事实见 [Engine 自有对话入口的形态比较](../research/engine-entry/report.md).

## Answer

用户 11-11 在三个候选 (Engine 自绘终端界面, Engine 提供的本地网页, 复用 Codex 与 Claude Code 自己的交互界面) 中选了本地网页, 并补充 (原话): "本地网页, 但会也监听外部请求, 这样用户在其他地方也能访问到. 目前暂时不需要用户名密码, 但需要和状态页一样的 "用授权码添加设备" 逻辑." 其中 "状态页" 指用户自用的一个本机网页服务, 它对局域网开放 HTTPS 访问, 新设备第一次连接时输入在本机生成的一次性授权码, 换得该设备的凭据, 之后每次请求都核对设备凭据, 设备可以逐个撤销. 以下是 Main Agent 对答复的理解, 11-12 记录.

- 首版入口: Engine 自带的网页, 作为 [定义 Engine 驱动流程的运行合同](07-define-engine-runtime-contract.md) 中事件流加命令接口的客户端. 不只监听本机回环地址, 局域网和远程设备也能连接, 所以远程与手机使用是首版要求, 不是以后的扩展.
- 访问控制是入口的必备部分: 首版不设账号密码; 非回环访问一律走 TLS; 未配对的设备只能看到配对页; 设备第一次连接时用一次性授权码配对 (授权码只能从已信任的一侧生成, 即本机命令或只监听回环地址的控制通道, 不按请求的来源地址判断是否本机 (07 的 Conversation entry and harness routing 节), 短时有效, 限制尝试次数), 换得设备凭据, 之后每个请求核对设备凭据; 已配对设备可以列出和撤销; 凭据与授权码只存哈希, 放在用户私有运行状态中. 批准请求和待答事项只对已配对设备展示和接受应答. 证书来源见 HTML client 节; 默认端口, 凭据有效期, 配对尝试上限等参数由规范正文定.
- 不采用复用 harness 交互界面的形态 (它让用户的话先进入 harness, 与 Engine 先接收用户的话相左). 终端界面以后如需要, 可以作为同一接口的另一个客户端再加, 不进首版. 用户没有要求把 Engine 暴露为 ACP agent, 首版不做.
- 影响: Engine 对外监听网络连接, 是 Engine 宿主进程的攻击面; Engine 的语言与实现要把这一点计入, 见 07. Windows 原生运行的验证要求在规范正文中写明.

### HTML client

用户 11-14 定首版只做 HTML 界面, 不做原生客户端 (原话见 Comments); HTML 能做什么按 11-18 的逐项核对 (任务 v1-html, v1-htmldec).

- 形态: 同一套网页在桌面与手机浏览器中使用, 可以安装成网页应用 (PWA: 加到主屏幕, 独立窗口). 不做原生客户端, 因为手机上要为 iOS 与 Android 各做一个 app, 工作量大增.
- 对话: 文字输入; 图片可以粘贴, 拖放或从文件选择; 语音输入见下条 (1.0 不做). 流式显示, 中断, 批准请求, 待答事项, 查看改动都经 07 的事件流加命令接口实现.
- 语音输入: 1.0 不做 (用户 11-18, 原话见 Comments). 能做已由本地测试确认 (任务 v1-asrtest2: 原版 SenseVoice 在 90 句语料上错误率 0.139); 以后要做时调用外部 API 转写, 不在本地运行模型. 浏览器端按 16 kHz 单声道 PCM 采集 (AudioWorklet) 的核对结论保留, 供以后参考.
- 远程必须 HTTPS: 麦克风, Service Worker 与 PWA 安装只在安全上下文 (HTTPS 或本机 `localhost`) 中可用, 用 `http://<局域网地址>` 访问只剩文字对话.
- 证书 (用户 11-18 D38, 选 A): 默认由 ARW 自带本机证书, 做法同用户自用的状态页: Engine 生成并保管一个本机私有 CA, 名称约束只允许本机名和私有网段; 服务端证书由该 CA 签发, 到期前自动续签, 续签不换根证书, 已装根证书的设备无需重装; 每台设备装一次根证书 (步骤与私钥保管见 Security of the HTML entry 节). 用户可以改用自己的证书 (给出证书与私钥文件路径, 例如 Tailscale 或自有域名的证书), 这样设备不用装根证书; 用户自己的证书由用户负责续期. 未采用: ARW 不管证书, 只用用户提供的证书 (装完不能直接远程使用, 要先有 Tailscale 账号或自有域名). 不在同一局域网时, 要用户自己有 VPN 或公网入口, 证书只解决信任, 不解决连通.
- 断线与锁屏: 手机锁屏或切到别的应用时浏览器会断开连接, 回到前台后按事件序号续接 (07), 消息与状态以 Engine 记录为准, 不丢.
- 不做手机消息推送 (用户 11-18 D39, 原话: "我们不做手机消息推送, 不是以后再做."): 不用 Web Push, 不向浏览器厂商的推送服务发消息, 不为此保存订阅或推送密钥, 也不列为以后再议. 手机锁屏或切到别的应用时不会收到 "有事等你批准" 的提醒; 用户回到页面后按事件序号续接, 即可看到待批准事项和待答事项 (07 的断线续接).
- 不支持或以后再议 (HTML 做不到, 不为它们做原生界面): 全局快捷键按住说话; 锁屏或后台期间保持连接与录音; 从别的应用分享到 ARW; 后台同步. 浏览器限制: Firefox 桌面不能安装 PWA.
- 未核实: iOS 上的行为 (采样率, 锁屏后断开) 要在 iOS 真机上验证, 列入规范正文的验证要求.

### Security of the HTML entry

D38 只定了本机私有 CA, 名称约束, 自动续签, 每台设备装一次根证书, 可换用户自己的证书. 本节把装根证书的步骤与私钥保管写成要求; 具体内容是 Main Agent 参照用户自用状态页的做法 (它的步骤用户已熟悉) 自定的取舍 (Main Agent 可改), 有效期, 文件位置, CA 何时生成 (例如首次启用远程入口时) 等参数由规范正文定.

- 本机私有 CA: 名称约束只允许本机名和私有网段; 因有名称约束, 根私钥即使泄露, 也只能签发这些名称与地址的证书, 不能冒充公网网站. 各手机系统是否都执行名称约束未核实, 列入规范正文的验证要求.
- 私钥保管 (自定): 根私钥与服务端私钥只存在运行 Engine 的那台机器上, 放在用户私有运行状态目录中 (目录与文件只有当前用户可读写, Windows 上按当前用户的访问控制), 不进 Git, 不随日志, 报告或诊断包输出, 不通过网页入口提供下载, 不发给任何设备; 设备只拿到根证书 (公钥). 服务端证书到期前由 Engine 自动续签, 用同一根证书, 不需要用户操作. 重新生成根证书会使所有设备要重装, 只在用户明确要求时做 (比如怀疑私钥泄露).
- 装根证书的步骤 (自定): 根证书只在运行 Engine 的那台机器上 (回环地址的页面或命令) 提供下载, 并显示它的 SHA-256 指纹; 用户把它传到每台设备 (Engine 运行在远端机器上时, 用户要先登录那台机器取证书, 这是代价), 核对指纹后按系统导入: Windows 导入当前用户的受信任根证书颁发机构; Android 在设置的安全, 加密与凭据中安装 CA 证书; iOS 先下载描述文件并安装, 再到 通用, 关于本机, 证书信任设置中为该根证书启用完全信任; Firefox 不读系统证书库, 要在它自己的证书管理器的证书颁发机构页导入. 不提供让未信任的设备绕过证书警告的做法, 也不在 HTTP 上提供根证书下载, 因为那会让证书下载本身可被替换.
- 与配对的关系: 装根证书只解决设备信任 Engine, 不授予访问权; 访问仍要一次性授权码配对和设备凭据 (见 Answer 的访问控制).
- 改用用户自己的证书时, 根证书的安装与私钥保管由用户负责, Engine 只读取用户给出的文件, 不修改它们.

### Free replies in the conversation entry

用户 11-14: 规则细节在输出时失效, 用户听不懂 (原话见 [定义规则到 graph 的转换与 Engine 按 graph 执行](22-define-rule-to-graph-conversion.md) 的 Comments). Agent 节点交给用户的文字是输出 schema 的字段 (22), 由 Engine 在交给用户前检查 (07 的 Before text reaches the user 节); 对话会话的自由回复时刻不可预知, 不能在固定的一步注入, 所以入口另做以下几件事. 11-14 任务 v1-rulecue 起草, 原待用户确认的两处已由用户 11-14 D29, D30 定下 (见 Comments).

- 每轮提醒: Engine 把用户的每条消息交给对话会话时, 在末尾附一行约 80 字符的提醒, 依次是: 用配置的回复语言回复; 不用内部编号, 节点名和未解释的缩写; 问用户走 `ask-user`: 标题即问题加推荐, 只补缺的, 选项写结果. 最后一句压缩了 22 中 `title`, `situation`, `options[].meaning` 的字段说明, 不再泛称 "按其字段写", 因为字段名本身不告诉会话该怎么写. 提醒文字是管理层参数 (22), 措辞按 14 的原型实测调整. 只附在用户消息后, 不附在流程事件后; 代价是提醒留在会话历史中, 100 轮约 8K 字符.
- 要用户决定的事走 `ask-user`: 对话会话的输出 schema 与其他 Agent 节点一样含 `ask-user` (22), 入口把它渲染成待答事项, 字段与检查相同. 自由文字中夹带的决定请求无法机械认出, 只靠提醒, 由 14 的验收数据看效果.
- 事后检查 (用户 11-14 D29, 状态页选 A): 回复照常边生成边显示; 回复结束后按 07 的 Before text reaches the user 节检查, 有命中时在同一会话退回改写一次, 入口收到 07 的 "回复替换" 事件后用改写版替换原回复, 原回复折叠在其下, 可以展开查看. 用户可能已经读到原文, 这是为保留流式显示接受的代价. 未采用: 先缓冲到回复结束, 检查后再显示 (不会看到原文, 但每条回复都要等整段写完).
- "没看懂": 入口在每条回复和每个待答事项旁提供 "没看懂" 按钮, 点了等于对该条运行 `wait-what` Skill (为不熟悉项目的读者补全背景重讲), Engine 把它发给原会话 (待答事项发给提问的会话), 重讲版同样过 07 的检查. 用户在对话中写的 "听不懂" 一类的话按 14 的有限词表认出, 与按钮一样计数, 消息照常交给对话会话.
- 回复语言 (用户 11-14 D30): 用户级配置新增一项回复语言, 安装时选定 (配置项见 [确定判断模型与兼容端点的安装与配置](20-decide-installation-and-configuration.md) 的 Reply language 节); 每轮提醒与 Agent 节点消息末尾的提醒写明它, 07 的语言检查按它判. 不另设允许缩写表: 仓库根 `CONTEXT.md` (ARW 现有的术语表, 每个采用仓库自己维护) 中定义过的名称和缩写视为用户认识, 是 07 缩写检查的白名单; 不在其中的仍要解释或改写. 用户级指令文件 (如 `~/.codex/AGENTS.md`, `~/.claude/CLAUDE.md`) 中的其他表达偏好仍由 harness 自己加载, Engine 不解析它们.
- 两个 harness 都适用: 提醒, 检查与改写都由 Engine 做, 与 harness 无关. 同类遗忘在 Claude Code 一侧也出现过 (用户级规则要求简体中文而回复成英文).
