## Premises

正文按以下已定前提写, 不再讨论:

- 1.0 是新建的独立仓库, 从新目录重写; 0.x 的规则, spec, ADR 与 Skill 只作历史参考 (用户 11-14, 见 13, 17).
- 首版只支持 Windows 与 Linux (含 WSL); Codex 与 Claude Code 完全对等 (04).
- 对话入口只做 HTML 网页, 不做原生客户端 (19); 1.0 不做语音转写 (用户 11-18, 见 Feasibility 节).
- 判断模型可选, 只做提示, 首版不配 (D24, 18).
- Engine 用 Rust 写 (任务 v1-langdec, 11-18); 复核条件由任务 v1-rust 写进 07, 正文照 07 写.
- 验收看三项: 墙钟, 评分 (Reviewer benchmark 与真实缺陷检出), 费用; 高智能请求数只作观察 (D34, 11).
- 规范正文写在 1.0 新仓库中将来生效的位置 (D35, 06).

## Spec location and layout

- 位置 (D35): 1.0 新仓库. 每章一份长期规范 `docs/specs/<章名>/spec.md`, 术语在仓库根 `CONTEXT.md`. 不另建 ADR 目录: 规范呈现规则本来要求每项重要规则写明理由, 决定连同理由写在拥有它的章里, 一个事实只有一个权威来源; 以后确有跨章且难以撤销的决定再按需加 ADR.
- 理由 (每章一份而不是一份大文件): 0.x 的单份长期规范已有约 240 KB, 一个实施 issue 只用到其中一小段. 1.0 的就绪记录按 spec Input 冻结 (09), 并行落盘时 "被引用的 spec 有交集" 会使就绪记录失效 (10 的场景 2); 按章分文件后, issue 的 Input 只列相关章, 改一章不会让引用其他章的就绪记录全部失效. 分章也正好对应按章分片审查 (06) 与逐批编写.
- 每章的写法按 0.x `docs/agents/specification-presentation.md` 的要求 (新仓库将来自己的写作规则以迁入的为准): 先写情境与理由, 再写行为, 状态变化与失败处理, 最后写验收场景. 场景写明发生在哪个阶段, 已产生和未产生的影响, 从哪里继续.
- 验收场景写在各章末尾的 Acceptance scenarios 节, 由 "验收与评测" 一章汇总成清单并定义口径, 不重复场景正文.

### C01 Overview and terms

- 行为: 1.0 中由 Engine 里的确定性流程 (graph) 驱动用户与高智能 Agent, 而不是由 Main Agent 读规则推进. 角色: Engine; 对话会话 (用户选定模型, 自由对话与分给它的高智能步骤); worker 与 Reviewer 会话. Engine 对所有会话一视同仁, 区别只在按工作选的模型. Git 写入只由 Engine 执行. 用户批准点是流程中的等待用户步骤. 覆盖全部现有工作流, 一次做完, 不与 0.x 共存.
- 理由: E5 与 E5b 的误判 (规则当时已存在却没照做) 与 E1 中规则流程类请求占 worker 请求 65%; 目标是更快, 评分不降, 更省 (D34), 而不是减少请求次数.
- 可观察结果: 三项目标与观察项列表; 术语表 (`CONTEXT.md`): Engine, 对话会话, 流程定义, 流程实例, 节点全名, 仓库层, 本机层, 写入令牌, 预置答案, 审核包等; 保留的 0.x 术语: Spec Readiness, Commit Audit, Workflow Distribution, Managed Content, Repository Profile, Application Leader/Member (13).
- 验收: 读者测试, 没参与 0099 的读者读完本章能答 "谁推进流程, 谁写 Git, Agent 怎样影响分支, 判断模型不配时怎样". 由全局一致性审查核对术语.
- 待定: 1.0 新仓库的正式名称与 GitHub 仓库 (06).

### C02 Engine process, sessions and failures

- 行为: 每个用户一个常驻 Engine 进程 (Rust), 私有状态库; 两个 harness 的会话层 (Codex App Server 线程, Claude Code stream-json 会话进程). 选模型分两段: 写任务概要的 Agent 步骤同时输出难度等参数, Engine 用配置中的映射表对到模型与推理强度; 一项工作自始至终一个会话一个模型, 压缩后照常继续. 会话做完一步不关闭, 空闲超过 `sessionIdleMinutes` (初值 30) 或名额不够时回收, 记录保留, 再用时续接. Git 写入只由 Engine 执行, 保证方式是检测: 步骤结束先终止本会话的命令子进程, 再核对 `HEAD`, 全部引用, 索引摘要, `.git/config` 与 hooks; 每个写入步骤开始前与每次暂存提交前再比较一次. 另加不覆盖用户设置的窄范围拒绝层 (尽力而为). Agent 步骤超时先提醒交付, 再超出就问用户, 不自行中断. 崩溃恢复不接回执行中的回合, 按会话记录判断回合是否完成. 恢复点 (08 的 Restore points 节): 每个写入步骤开始前 Engine 用临时索引把该步写入范围写成快照, 挂在私有引用 `refs/arw/baseline/<实例>/<步骤>` 下, 只供用户停止后手动恢复, 不做自动回退; `done` 后删除, `stopped` 与 `cancelled` 保留到用户回退或丢弃; `git push --mirror` 会推送这些引用, 正文写明.
- 理由: 一个进程不复制状态库, 名额与恢复; 会话常驻保留理解并复用提示缓存; 检测而非阻止, 因为能运行 `node` 的会话总能间接执行 Git, 原生 Windows 的 Claude Code 也没有沙箱.
- 状态变化: 会话 新建 -> 执行回合 -> 空闲 -> 回收 (记录保留) -> 续接; Git 核对不通过时实例转 `stopped`, 停在可恢复状态.
- 可观察结果: 步骤记录 (会话身份, 模型与推理强度, 起止时间, 交接延迟, 额外请求, 首个响应时间, 高智能请求数, token, 重起会话的标记, 所用裁决).
- Efficiency and resource budget 节 (07 的预算在此落位): 每个 Agent 步骤的交接不超过 0.5 秒 (目标低于 0.1 秒) 与 1 个额外请求; 每条用户消息经 Engine 的路由附加延迟不超过 0.5 秒; 模型首个响应单列, 不计入. 空闲常驻的内存与 CPU 上限: 07 已引用实测; v1-lang 的对写实验测得 Rust 实现空闲 RSS 约 2.9 MB, 峰值约 7.4 MB (n = 8, 2 路并发各 2 万事件加 SSE), 正文据此定上限 (建议常驻峰值 RSS 不超过 20 MB 量级, 留出真实依赖的余量), 并写测法 (Engine 空闲 10 分钟的常驻内存与 CPU 均值, 不含 harness 与模型进程), 实施早期按真实技术栈复测.
- 验收场景:
  - 正常: 一个 issue 实施加两轮审核, 步骤记录显示 worker 与 Reviewer 各只有一个会话身份, 模型不变.
  - 正常: 会话空闲 30 分钟被回收, 下一步按会话 ID 续接, 该步标出重起会话, 交接计入预算.
  - 失败: 会话用 `node -e` 改了索引; 步骤结束核对发现, 实例停在可恢复状态, 恢复点可用; 后续步骤未开始.
  - 失败: 脱离的后台进程在核对之后写了 Git; 下一个写入步骤开始前的比较发现, 实例停下交用户.
  - 失败: Engine 在写入步骤中崩溃, 回合没有最终输出; 重启后在原会话发 "上一回合被中断, 先检查工作区再完成本步", 不回到基线.
  - 失败: 额度耗尽或认证失败; 实例转 `stopped`, Engine 不自动换模型, 用户选择换模型后按交接消息继续.
  - 失败: Agent 步骤超出时间预算; 先提醒交付, 再超出时问用户, 等答复期间会话照常运行.
  - 恢复 (08 的场景 3): 用户在实施中途停止实例; 入口列出各写入步骤前的恢复点, 用户选定一个, Engine 先另存当前状态再恢复该点; 用户也可以不回退, 改动留在工作区. 回退本身失败时报告用户, 不反复重试.
- 待定: Claude Code 能否只终止子进程树而保留会话进程, 以及 Codex 后台终端实验接口的版本核对 (都待原型或实施早期核实, 见 C17).

### C03 Flow instances and coexistence

- 行为: 流程定义 = 发布层, 仓库层, 本机层三层合并 (C04) 加 Engine 原语. 步骤只有四类: 确定性操作, 判断 (可选提示), Agent 步骤, 等待用户. 下一动作由流程定义, 当前状态与上一步结果唯一决定; Agent 只能经输出 schema 的字段影响分支; 定义没覆盖的情况转等待用户. 实例每步先持久化再执行下一步, 绑定启动时的定义版本. 栈 (调用子流程), 汇合式分支, 与 `spawn` (另起实例, 不可等待, 计入无环检查). 停止的单位是顶层实例. Agent 名额满时实例转 `waiting-capacity` 排队: 持有写入令牌的写入链在前, 其余按就绪先后. 同一会话一次只执行一个回合. 决定走向的配置在启动时绑定, 连接与资源配置随用随读, 用户裁决随时生效.
- 0.x 对照, 正文写一句: 0.x 后台管理进程名额满时立即返回容量不足; 1.0 删除了 `arw background-agent` (13), 只剩 Engine 步骤排队这一种行为.
- 对话会话占名额: 按 07 的 "会话一视同仁", 对话会话是普通会话, 占名额, 空闲回收照常. 用户发来消息而名额已满时它排在哪里, 07 没有定 ("首版不设仓库间或工作流间的优先级"), 交用户决定 (见 Open questions 节); 答复前正文按 07 现有排序写.
- 做完一项接下一项: 0099 没有 issue 讨论, 由谁发起要用户定 (见本大纲 Open questions 节). 正文在答复前只写: Engine 只在用户发起或批准的流程中启动 Agent 会话, 流程自己不能用 `spawn` 接下一项 (会成环).
- 状态变化:

| 状态 | 进入条件 | 离开条件 |
|---|---|---|
| `running` | 启动或等待结束 | 步骤需要等待, 失败, 完成或被停止 |
| `waiting-user` | 等待用户步骤, Agent 问用户, 定义没覆盖的情况 | 用户答复 (回到同一节点) 或停止 |
| `waiting-subflow` | 调用子流程或汇合式分支未全部返回 | 子流程全部返回 |
| `waiting-writer` | 写入步骤需要令牌 | 按进入先后取得令牌 |
| `waiting-capacity` | 名额满 | 名额释放, 按上述顺序 |
| `stopped` | 失败 (Git 核对, 额度, 自检, 格式两次不合格等) | 用户选择继续 |
| `done` / `cancelled` | 完成 / 用户停止 | 终态 |

- 可观察结果: 入口列出全部实例, 当前步骤, 等待原因, 队列位置与等待时长; 等待时长记入步骤记录.
- 验收场景 (07 Coexisting instances 节):
  1. Commit Audit 的两个 Reviewer 与完整验证作为三个分支运行, 名额只够两个时第三个排队, 全部结束后汇合继续.
  2. 实施实例 `spawn` 一个规划实例后被用户停止, 规划实例继续运行.
  3. 两个分支在同一节点同一情况上问用户, 入口只列一项, 一次答复后两个分支都继续.
  4. 持有令牌的实例等用户期间, 其他实例的只读步骤占满名额; 用户答复后它的下一步先于更早排队的只读步骤取得名额.
  5. 用户在一个实例中选了常设裁决, 另一个运行中实例到同一节点同一情况时不再停.
  6. 用户改了仓库配置中的轮次参数, 运行中的实例按旧值走完, 新实例用新值.
  7. 失败: 用户手工改了 issue 的 `Status`; 实例发现与仓库不一致, 以仓库为准停下请用户确认.
  8. 失败: Engine 升级后, 停在等待状态的实例在新版本中找不到同名步骤, 停下报告用户.

### C04 Graph, layers, migration and command-line tool

- 行为: 迁移后 graph 加节点说明是流程的唯一权威 (D26). 格式按试转换: 每个子流程一个 JSONL 文件, 首行是子流程头 (`flow`, `desc`, `entry`, `returns`), 之后一行一个自足的节点; 节点全名 `子流程/id`; `call` 节点的 `next` 键必须等于被调子流程的 `returns`; 每个子流程与节点都有 `desc`. Agent 节点有输出 schema, 工作键 (会话策略), 默认档位, 写入范围; 实施类 Agent 节点带逐条验收标准的 `criteria` 字段 (09); Agent 问用户由 Engine 代办, 答复后回到同一节点. 原语只有接口, 实现在 Engine 代码中. Layers 节: 发布层 (安装方不可改), 受 Git 跟踪的仓库层, 本克隆被 Git 排除的本机层; 上层记录带 `base`, 被补丁的节点在升级后变化即过期, 交用户复核. Verification 节: 第 1 层静态校验 (接线, 无环, 提交原语与 `spawn` 成环, 正式关卡不可绕过), 第 2 层分支测试, 生成的流程说明与 graph 一致. 一次性迁移: 高智能模型按迁移专用 Skill 把 21 划入转换范围的规则转成 graph 与新原语, 源映射只在迁移期间核对完整性, 之后不保留. 源码检出 graph 只在 1.0 源码检出中加载. 命令行工具: 查询, 改名 (同步全部引用), 上层记录子命令 (含台账, C05).
- 理由: 结构拦截比读规则可靠 (E2: ARW 流程内的 A 类误判 8/8 由 graph 结构拦截); 读改实测两组都是 8/8, 满足 D26 的 "graph 可读可改" 前提; 分层让仓库与本机的调整不改发布部分, 升级时能检出冲突.
- 状态变化: graph 版本随 Engine 发布; 上层记录 有效 -> 过期 (base 不符) -> 复核后重新确认或撤销.
- 可观察结果: `graph check` 的错误输出, 生成的流程说明, 流程页上节点所在的层 (C12).
- 验收场景 (22 的 Interfaces 节):
  1. graph 静态校验失败时 Engine 不开工.
  2. graph 升级后运行中的实例按绑定的旧版本完成.
  3. 判断节点题目模板变化使该类提示停到重新离线评测通过.
  4. 互换一个节点两个结果值的去向被分支测试拦住.
  5. 生成的流程说明过期时源码仓库检查失败.
  6. 用命令行工具改名后全部引用同步且静态校验通过.
  7. 一个仓库的仓库层在其他仓库中不加载.
  8. 上层补丁改边绕过正式关卡时合并校验失败, 该仓库不启动新实例.
  9. ARW 升级改了被补丁的节点后记录过期, 实例到达该节点时等用户复核, 过期的预置答案照常问用户.
  10. 记录的 ARW 版本高于本机时提示升级.
  11. Agent 节点 (含 Reviewer) 问用户后回到同一节点继续.
  12. 分支中含提交原语或 `spawn` 构成环时静态校验失败.
- 待定: 原语目录的粒度 (试转换的 commit 流程用了 24 个); 仓库层与本机层两个目录的名称; 22 Graph shape 节末段列出的尚未表达的情形. 这三项由本章正文定.

### C05 Ruling ledger and consistency check

- 行为: 待答事项带 `key` (机械算出的情况键) 与 `cause`. 用户答复时可选 "常设" 及层 (仓库或本机); 只有常设答复写成上层记录 (节点全名, 情况键, 答案, 原因, 修复, `base`). Engine 在每个 Agent 节点开始时注入相关裁决, 在每次进入等待用户前匹配常设裁决, 匹配到就自动作答并写入步骤记录. 预置答案只在现有选项中选一个, 不改 graph 形状, 所以不随实例绑定. 仓库层写入需要令牌, 本机层由 Engine 原子写文件, 写前用 `git check-ignore` 核对该目录被忽略. 一致性检查是 C04 静态校验的扩展: 文档禁令与节点能力的矛盾, issue 验收项引用提交后事实等, 在规划阶段报出. 与 09 的处置台账 (单次提交尝试的 Reviewer 发现) 不同, 不合并.
- 理由: 第五目标减少停机点; E5b 中 S2 停机多是同一类情况反复问.
- 状态变化: 记录 有效 -> 过期 (节点改动或 ARW 升级) -> 复核 (重新确认或撤销); 撤销从下一次匹配起生效, 已走过的步骤不重做.
- 可观察结果: 步骤记录写明所用裁决; 命令行工具按节点列预置答案, 列过期与待修.
- 验收场景 (23 的 Interfaces 节, 另加升级复核一条):
  1. 同一情况第二次出现时按常设的预置答案继续, 或附带已有裁决.
  2. 未选常设的答复不写进 graph, 下次照常问.
  3. 本机层的记录只在本克隆生效, 仓库层的随提交在其他克隆生效.
  4. 节点改动后旧记录过期, 照常问用户并列入复核.
  5. 夹具中重复同一 Reviewer 结果的环在上限内离开.
  6. issue 验收项引用提交后事实时在规划阶段报矛盾.
  7. ARW 升级后上层记录过期的复核: 升级改了某条常设裁决所在的节点; 实例到达该节点时不自动作答, 照常问用户并附上旧裁决, 用户可重新确认 (记录的 `base` 更新) 或撤销.
  8. 失败: 用户手工删掉 `.gitignore` 中本机层那一行后常设一个仅本机的答案; Engine 拒绝写本机层并提示补写 (与 C13 共用, 由 C13 持有).

### C07 Review gates and Reviewer protocol

- 行为: 每个关卡回合按 确定性检查, 提示类判断 (只在配了判断模型时), 冻结, 正式审核, 处置, 修复 的顺序执行. 关卡结论只来自 Reviewer. Reviewer 是 graph 中的普通 Agent 节点, 与被审工作分开的会话; 复审回到原 Reviewer 会话, 处置与修复回到原 worker 会话. Engine 组装审核包 (Role 与规则副本内联注入, 本轮输入). 不设覆盖清单, 不再每轮抽查 (D15). 冻结输入变化时按 09 失效. 就绪记录版本 8; haiku 回退删除. Spec Readiness, Commit Audit 的门禁语义与 Reviewer 独立性原样保留 (13). Reviewer 步骤到 30 分钟向用户报告并询问, 是 C02 超时规则的特例.
- 理由: 关卡占活动时间最多 (墙钟研究: Reviewer 占 67%); E2 中 Reviewer 的请求节省几乎全部来自审核包 (没有审核包时请求比 0.96).
- 状态变化: 回合 冻结 -> 审核中 -> 有发现 (处置, 修复, 下一轮) / 通过; 就绪记录 有效 -> 失效.
- 可观察结果: 每轮的冻结 `tree`, 各轴结论, 处置台账, 轮数, Reviewer 回合时长.
- 验收场景 (09 的 Scenarios 节):
  1. 预检拦下问题 (配了判断模型且预检已启用).
  2. 多轮审核沿用会话.
  3. Reviewer 输出格式不符: 同一会话重答, 两次仍不合格时该轮作废, 实例停在可恢复状态.
  4. 修复不完整 (配了判断模型且修复核对已启用).
  5. 实施开始后 spec Input 变化: 只核对 subject, 就绪记录仍有效.
  6. 一轴先返回: 立即开处置, 另一轴随后返回; 同一会话不并行两个回合.
  7. 就绪记录版本 7 在 1.0 中不授权.
- 风险: 原型 s2 中审核包没有缩短 luna 的 Reviewer 回合, 未达到 09 的 "至少 10%" (见 C17).

### C08 Parallel flows and write isolation

- 行为: 每个仓库一个写入令牌, 按进入 `waiting-writer` 的先后发放, 只在没有未提交修改时释放. 非持有实例只读工作区, 草稿写在实例自己的 `.tmp` 临时工作区; 冻结输入 = 基准提交 (`HEAD`) 加草稿; 取得令牌后按与新 `HEAD` 的差异落盘. 每步结束的核对加上已跟踪内容的归属检查. 没有投机写入, 不需要屏障与跨实例回退.
- 理由: 草稿与就绪审核可以和别的实施并行, 又不需要树对象视图之类的复杂机制 (批判审读一.5).
- 状态变化: 令牌 空闲 -> 持有 -> 释放; 实例 `waiting-writer` -> `running`.
- 验收场景 (10 的 Scenarios 节): 草稿与就绪并行; 落盘时有交集 (就绪记录失效, 增量复审); 测试与修复并行 (测试绑定修复前的树); 越权写入 (下一次冻结或提交前停下交用户). 另含 20 的三个忽略规则场景, 由 C13 持有, 本章引用.

### C09 Optional judge-model hints

- 行为: 首版可不配; 配置只需一个端点 (20). Engine 在进程内调用 `/v1/systemone` 兼容接口, 只用 `choice` 与 `noul` 题型; 结果只决定是否把一条提示交给正在干活的会话核实, 不驱动流程. 调用失败或超时该题不提示, 流程照常, 不打断用户. 每类提示过了离线门槛 (阈值以上精度不低于 0.95, 覆盖率不过低) 才启用; 线上满 100 条后无效比例超过 5% 停用; 模型版本或题目模板变化时停到重新评测通过. 托管评测只发公开仓库的案例; 调用记录默认不存 `state` 原文.
- 理由: D24, 用户的使用条件 (比托管小模型快很多倍且准确率不明显降低, 18); 现有本地候选不满足, 所以首版不配.
- 验收场景: 20 的三个端点场景 (没有配判断模型; 配置机构内部端点; 运行中端点不可用) 与 08 的场景 1, 2 (需要用户授权的分支字段加可选提示; 没有可用 Agent 步骤时走保守分支).

### C10 Text that reaches the user

- 行为: `ask-user`, `wait-user` 的问题模板与 `report` 是输出 schema 的字段, 每个字段带字段说明; Engine 渲染后交给用户. 交出前做 07 的机械检查, 命中时退回同一会话改写一次, 改写后仍命中也照常交出并记录. 字数按 07 的预算只记录, 不退回. 对话回复按 19 做 "回复替换". 回复语言按 `replyLanguage` (20) 检查.
- 问用户的写法 (本大纲按 askmeasure 定):
  - 补背景: 答案依赖的项目概念 (如 ledger, `.scratch`, 审核轮次) 换成平白的说法, 或附一个短语解释; 只有 `CONTEXT.md` 中的术语可以不解释. 理由: 两侧盲读的失败几乎都是读者自报 "缺项目背景, 无法作答".
  - 限长: 字段说明里写出 07 的字数预算 (取舍类 150-250 字, 要用户动手且不含命令 200 字, 含命令 350 字, 确认理解 80-200 字), 超出照样只记录, 不退回. 理由: 1.0 首稿平均比现行多 129 字, 22/25 题变长; 若按字数退回, 改写比例会接近全部, 远超 15% 的线.
  - 首稿过检查: Engine 在交出前机械地把它认得的发现编号 (形如 H12, M3, F1) 展开成标题, 与 07 已有的 Canonical ID 附标题同样处理, 不算改写 (这改了 07 的检查 2, 发现编号原属 "未解释的编号" 要退回改写; 正文按此写, 07 待下次改动时同步); 字段说明列出禁用写法 (全大写状态名, Skill 名, `HEAD` 一类的内部词). 理由: 首稿检查命中 36-40%, 命中主要是审核发现编号, 其次是 BLOCKED, SKILL, HEAD; 机械展开可以去掉其中最大的一类, 估计减少 6-7 题的命中.
  - 不再要求写 "为什么要用户定" (14 的 Comments).
- 状态变化: 文字 首稿 -> 检查 -> (命中) 改写一次 -> 渲染交出; 每份记 检查命中, 是否改写, 字数, 改写请求数与耗时.
- 可观察结果: 入口显示的是渲染后的文字; 步骤记录有上述各项; 每周报告 "听不懂" 一类信号的次数.
- 验收:
  - 原型阶段: 用 askmeasure 的同一批 25 题, 同一要点与打分流程复测, 1.0 组仍按 14 的 Comments 构造约 12 小时会话后段的上下文 (D32 的主口径; askmeasure 只有 0.01-1.22 小时的短会话, 只作下限参考), 通过线按 D31 (看不懂率不超过现行基数的三分之一且不超过 10%, 改写后仍命中不超过 2%, 需改写不超过 15%, 渲染后平均字数不高于现行, Codex 与 Claude Code 分别达到).
  - 上线后: 主指标是每 100 份文字中用户回 "听不懂" 一类的次数, 信号与词表的正例反例按 14 的 Comments, 只按所列例子判定.
- 验收场景:
  1. 正常: worker 问一个取舍, 字段完整, 检查无命中, 入口显示渲染后的文字, 字数记入步骤记录.
  2. 首稿含 "H12 未修"; Engine 展开为该发现的标题, 不计改写.
  3. 首稿含禁用写法; 退回同一会话改写一次, 改写后无命中.
  4. 改写后仍命中; 照常交出, 记为 "改写后仍命中".
  5. 交互安装选了中文, 对话会话回了一整段英文; 语言检查命中, 改写一次, 入口用中文版替换 (20 的场景).
  6. 用户回 "啥意思"; 记一次信号; 用户回 "看懂了, 继续" 不计.
- 风险: "补背景" 与 "平均字数不高于现行" 互相拉扯; 复测达不到时如实报告, 由用户定调门槛还是改写法, 不自行改门槛.

### C11 HTML conversation entry

- 行为: Engine 自带网页, 桌面与手机共用, 可装成 PWA. 监听分两类, 按监听口认证, 不按来源地址认本机: 回环控制通道只给本机命令行; HTTPS 入口也接受局域网与远程请求 (用户 11-11 的答复, 19). 设备第一次连接用本机生成的一次性授权码配对 (短时有效, 限次), 换得可撤销的设备凭据, 之后每个请求核对; 未配对的请求除配对接口外一律拒绝; 凭据与授权码只存哈希. 证书按 D38 (本机私有 CA, 名称约束, 自动续签, 每台设备装一次根证书, 可换用户自己的证书). 不做手机推送 (D39). 入口是 Engine 事件流加命令接口的客户端, 不持有流程状态, 可多个同时连接, 断线后按事件序号续接. 文字与图片 (粘贴, 拖放, 选择). Engine 按对话会话的模型把用户的话交给对应 harness. 1.0 不做语音输入.
- 理由: 远程与手机使用是首版要求 (19); 不按来源地址认本机, 因为 WSL 与端口转发下来源地址不可靠.
- 状态变化: 设备 未配对 -> 已配对 -> 已撤销; 连接 在线 -> 断开 -> 按序号续接.
- 验收场景:
  1. 新设备装根证书并用授权码配对后能对话与答复待答事项.
  2. 未配对设备的请求只得到配对页; 授权码过期或超过尝试次数后配对失败.
  3. 撤销一台设备后它的下一个请求被拒, 其他设备不受影响.
  4. 手机锁屏后回到前台, 按事件序号续接, 消息与待答事项不丢.
  5. 用 `http://<局域网地址>` 访问只剩文字对话, 页面说明原因.
  6. Engine 在 WSL 的 NAT 网络下, 配置命令报告局域网不可达及两条修正路径的步骤与代价; 未完成前入口只在本机可用, 流程不受阻.
- 待定 (正文定): 默认端口, 凭据有效期, 配对尝试上限, CA 生成时机. 待实施验证: iOS 真机行为, 各手机系统是否执行名称约束.

### C12 Flow page

- 行为: 网页入口中的 "流程" 页, 桌面与手机共用, 读与 Engine 同一套 graph 文件与读取代码. 一屏一个子流程, 默认逐层列表, 图只作宽屏可选视图, 路径摘要是第二视图; 面包屑进入与返回; 一个搜索框按节点全名, 参数, 原语与关键词定位; 每个节点与边标出所在层; 可叠加某个实例的当前位置与走过的路径; 过期的上层记录标出.
- 理由: D26 后 graph 是权威, 用户要能看懂流程; 从顶层子流程按需展开, 不一次铺开 74 个节点 (试转换规模).
- 验收场景: 读者在手机上从顶层找到某个节点, 说出它的去向与所在层; 叠加一个运行中实例时显示当前节点; 有过期记录的节点被标出. 可读性补测已做 (两组都是 12/12).
- 已定: 首版只读 (用户 11-18 定, 任务 v1-viewro 选 A); 本章不写编辑行为, 编辑经命令行工具 (见 ARW-v1 `docs/specs/flow-page/spec.md`).

### C13 Installation, configuration and harness compatibility

- 行为: 1.0 自己的安装: 固定安装目录, PATH 归属, 不降级, 安装维护前的静止核对 (含没有执行中的流程步骤), 控制与维护端口只绑定 `127.0.0.1`. 用户登录时自动启动: Windows 写当前用户 `Run` 项; Linux 用 systemd 用户服务 (`enable-linger` 由用户选); WSL 由 Windows `Run` 项启动并核对空闲关闭. 防火墙与 WSL 网络只检测与报告, 不自动修改. 用户级配置: 模型映射表, 角色键, 判断模型一节 (可空), `replyLanguage`. 仓库忽略规则 (D28): `arw workflow init` 把 `.tmp/` 与本机层目录两行写进受跟踪的 `.gitignore` 并用 `git check-ignore` 核对, 写入后归仓库所有, `workflow remove` 不撤. harness 版本漂移: 经兼容端点用本地或第三方模型的角色, 每个新的 (harness 版本, 端点, 模型) 组合先跑一次兼容自检.
- 理由: 远程入口要求 Engine 随登录启动; 跟随用户安装的 harness (D19), 只能靠自检发现兼容端点失效.
- 验收场景 (20 的 Scenarios 节中归本章的部分):
  1. 新仓库 `arw workflow init`: `.gitignore` 加一行注释与两行规则, `git check-ignore -q -- .tmp/probe` 退出码 0; 已有 `.tmp/` 规则时只加本机层那一行.
  2. 用户手工删掉本机层那一行后常设一个仅本机的答案: Engine 拒绝写本机层并提示补写, 补写后才能写.
  3. `arw workflow remove`: 两行与注释不动; 选择删除本机层目录时只删目录内容.
  4. 非交互安装没给回复语言: 不查语言, 入口状态提示设置.
  5. 用户的 Claude Code 自动更新后兼容端点返回 400: 下一回合前的自检失败, 流程停在可恢复状态, 报告给出上一个通过的版本与安装命令; 装回后从该步继续.
- 风险: 原生 Windows 的 Claude Code 没有沙箱, 拒绝规则不可靠, 只能靠 C02 的检测; Windows 防火墙需要管理员预建放行规则; WSL 常驻进程能否阻止空闲关闭待实施验证.

### C14 Moving from 0.x to 1.0

- 行为: 不就地升级, 不共存. 顺序: 各仓库进行中的工作先到静止点; 卸载 0.x (保留数据); 安装 1.0 (0.x 仍装着时拒绝); 1.0 接管每个已采用的仓库. 接管 (D37): `arw workflow init` 或 Engine 首次打开仓库时自动识别 0.x 写入的规则文件与 v2 锁, 一次替换, 作为一个非实施提交; 预检锁为 v2, 无旧格式 Artifact, 工作区与索引干净 (`.tmp/` 按路径排除). 1.0 在锁中写 `lockSchemaVersion: 3`, 使 0.x 运行时关闭式失败; Engine 遇到 v2 锁不开工. 1.0 不读, 不迁移, 不删除 0.x 的配置与状态库. 接管后跑接管后审核, 有缺口时创建一个补全 issue. 未进终态的实施 issue 在 1.0 下重跑 Spec Readiness. 支持一次手工退回 0.x.
- 理由: 1.0 必然改写 Reviewer Role 与就绪记录版本, 0.x 的记录本来就不能沿用; 版本门槛防止另一台机器上的 0.x 悄悄改回规则.
- 验收场景 (13 的 Interfaces 节):
  1. 0.x 仍在安装时 1.0 安装被拒, 提示先卸载.
  2. 有未提交工作时接管被拒.
  3. 0.x 运行时在 v3 锁仓库上执行 `workflow *` 失败.
  4. v2 锁仓库上 Engine 不开工, 提示先接管.
  5. 按 Failure recovery 节手工回退: 卸载 1.0, 重装 0.x, `git revert` 接管提交, 0.x 数据仍在.
  6. 跨版本的 Application 关联仍可同步.
  7. 接管后 `git check-ignore` 对 `.tmp/` 与本机层目录通过; 已有等价规则时不重复加; 规则只在 `.git/info/exclude` 时仍补写 `.gitignore`.
  8. 接管自动识别 0.x 规则文件并一次替换, 历史上只多一个提交; 1.0 状态库从空开始.
- 未核实: 用户是否在脚本或 CI 中调用 0.x 的门禁命令 (13).

### C16 Acceptance and evaluation

- 通过条件 (D34): 1.0 对照现行 ARW, 在同一类真实任务上:
  - 墙钟: 活动时间 (总墙钟减去等用户答复与空闲时间) 的合计比与逐流程中位比都不超过 0.85; 含等待口径与用户介入次数另报, 不作通过条件.
  - 评分: Reviewer benchmark 盲评分与真实缺陷检出不低于现行; 是否另设提高幅度待定.
  - 费用: token 费用或订阅额度消耗, 比值阈值待定 (等原型与任务 v1-splitrun 出数后由用户定).
  - 观察项: 高智能请求数, 规则与流程上下文占比 (实现时静态核对不超过 5%), 每天观察的误判率, 停机点次数, 用户推翻或要求重做的次数.
  - 不配判断模型也要达到.
- 墙钟基线 (本大纲定): 一律用与 1.0 同期新跑的配对对照, 同一批 issue 在现行 ARW 与 1.0 下各跑一遍, 用同一套脚本从记录里算; 不用历史记录作比较对象. Codex 与 Claude Code 各自对照, 各自达到. 历史数据 (Claude 侧每个实施 issue 15-25 分钟, Codex sol 侧中位 9.9 分钟) 只用于事先估计.
  - 理由一: 原型 s2 中新跑的对照比历史对照高约两成 (墙钟比 1.24, 区间 0.97-1.72; 高智能请求比 1.19), 模型版本与驱动方式都在变, 历史基线会把这部分变化算进 1.0 的收益或损失.
  - 理由二: 04 定两个平台完全对等, 而两侧的审核时长与机械请求占比不同 (墙钟研究明确 E2 的 Claude 结论不适用于 sol), 合在一起会掩盖某一侧不达标.
  - 代价: 验收测量量加倍. 达不到门槛时如实报告差距, 由用户定调门槛还是加做法, 不自行改门槛.
- 交给用户的文字: 按 C10 的验收.
- 判断模型: 只用于判断模型自身的取舍 (开着与关着某类提示比较费用, 墙钟与审核轮数), 不是 1.0 的验收对照.
- 场景清单: 汇总 C02 至 C15 各章的验收场景, 每条标明在原型, 实施验收还是上线后观察中核对.

## Open questions

- 做完一项接下一项由谁发起 (concur 研究的遗留, 0099 没有 issue): 流程不能自己 `spawn` 下一项 (`spawn` 计入无环检查). 候选: (A) Engine 工作队列, 用户一次批准一组项 (例如一张地图的前沿 issue), 一项到终态后 Engine 启动下一项, 对话会话可以往队列里加项; (B) 由对话会话在每项结束后发起下一项. 建议 A: 满足 07 的 "Engine 只在用户发起或批准的流程中启动 Agent 会话", 不为推进流程花对话会话的高智能请求, 对话会话断开或被回收也不影响推进. 这是用户可见行为, 交用户决定; 答复前 C03 只写现有约束.
